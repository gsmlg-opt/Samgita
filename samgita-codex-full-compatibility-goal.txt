The target is complete CLIENT/DRIVER compatibility with a real, immutable, version-pinned Codex app-server, initially rust-v0.163.0. The current reviewed baseline is Samgita 4fe354f2. Inspect actual HEAD and working-tree changes first; do not revert newer work. The existing adapter is only a restricted six-method/three-notification mapping layer. Merely expanding that table, adding generic JSON forwarding or passing its existing tests does not satisfy this goal.

Create and maintain repository documentation under docs/codex-app-server/ (reuse equivalent existing paths if appropriate): design.md, implementation-plan.md, goal.md, qualification.md, and a machine-readable compatibility manifest. These documents track execution; writing them is Phase 0, not task completion.

Mandatory execution sequence:
1. Pin exact upstream source, binary, schema and configuration. Generate and audit the complete manifest from pinned source/schema/tests, including all four message directions, every parameter/result variant, errors, legacy and experimental gates.
2. Implement a lossless native protocol layer and retain convenience mappings above it. Preserve complete data and errors; remove text-only and empty-parameter restrictions where upstream supports more.
3. Implement actual supported transports and supervised sessions/processes, handshake, bidirectional request correlation, full event delivery, deadlines, backpressure, cancellation, shutdown and truthful uncertain-outcome recovery.
4. Implement every capability family and every server-initiated interaction in the manifest. Approvals, user input, tools and full item lifecycles must work end to end, not become discarded notifications.
5. Integrate with Samgita's ordinary Agent/project/task model while preserving authorization, fencing and execution/review/acceptance separation. Provide independent consumer examples without database or Web dependencies.
6. Build schema tests, deterministic fault-injection tests, real pinned Codex binary tests, Samgita end-to-end tests and explicit external/platform acceptance profiles. A mocked Codex server does not prove compatibility. Disabled/unavailable behavior and enabled success behavior must be distinguished.
7. Complete the manifest and all applicable acceptance gates, run the required repository/hosted checks, update evidence and deliver commits/publication according to the established release policy.

Final completion requires all manifest entries and relevant field/behavior variants to have complete implementation and evidence against the declared upstream build and deployment matrix. Missing, skipped, mock-only or externally blocked requirements cannot be counted as verified. All required final local and hosted checks must correspond to the final source. At completion, report: pinned version/hashes; verified/missing/blocked manifest totals; implementation and regression summary; exact commands and real-binary/CI evidence; external acceptance and remaining platform risks; commit, push and release status with verified links.
